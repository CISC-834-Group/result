# Firefox JIT study methods

## Data collection and cohort selection

- Human proxy: 2021-11-30 through 2022-11-29, using author dates in UTC. This follows the team's script README and predates ChatGPT's public release. We use this period as a proxy for human development, although developers may have used earlier assistance tools.
- AI candidate cohort: 2025-11-01 through 2026-10-10. The end date is the supplied database's collection cutoff.
- Original baseline: the supplied replication package's `mozilla.csv`.

We exclude merges, backouts, automated commits and commits with no file changes. Following the team's pipeline, we also exclude imported `[fenix]`, `[focus]` and `[components]` histories, removing 4,843 commits from the human window. We obtain product and component from the Bugzilla issue referenced in the first line of the commit message. Changes without a product are included in the general model but excluded from the product models.

## AI screening

To identify AI candidates, we apply the keyword rules in the team's main branch. We flag a commit when its message matches a tool name or attribution pattern, or contains a robot emoji. We then apply author propagation: once a commit is flagged, subsequent commits by the same author are also flagged. A separate message-style score identifies additional candidates. The final candidate set includes commits identified by either method.

The content rules flag 11,470 of the 53,330 scanned commits. After applying the common exclusions and adding style-only matches, we obtain 9,603 candidates: 233 direct content matches, 9,031 propagated content flags and 339 style-only flags. Only 16 direct matches satisfy the attribution patterns, such as “Co-authored-by” and “generated by.” Matching these patterns does not confirm that the code was written by AI.

When we apply the same combined rules to the comparison period from 2019-11-30 through 2020-11-29, they flag 5,485 of 43,207 commits (12.69%). This result suggests that the rules also detect messages unrelated to modern generative AI. However, the historical commits have not been independently labeled, so this comparison does not provide a measured false-positive rate. For example, `d387f5c68c6260185c9f475c440dd95f5c3c5ce2` matches because its message discusses custom mouse-cursor objects, without an AI attribution. Author propagation can extend an ambiguous match to many subsequent commits. The resulting labels identify AI candidates, not verified AI-written code.

## Defect labels

The supplied database contains SZZ traces for recent fixes but lacks coverage for the human window. Missing public Bugzilla reports were collected for 2021-11-29–2022-11-30, and 10,371 candidate fixes were identified using the existing rules: a non-merge, non-backout, non-automated commit linked to an accessible issue of type `defect` and resolution `FIXED`.

We trace changed or deleted nonblank lines using `git blame -w` and accept an inducing candidate only when its date is no later than the issue report's creation time. For each cohort, we consider fixes through the final day of its window, without an additional observation period. We assign a zero label when this procedure finds no accepted evidence that a change introduced a defect. Such changes may still contain defects, particularly near the end of the observation window. The labels are therefore subject to right censoring.

To reduce the history traversed by SZZ, we define graph boundaries from the eligible human commit hashes. We independently checked all 748,783 commits excluded by the four boundaries and found no eligible target commits. A boundary commit therefore cannot be an eligible inducing candidate. To check this restriction, we compared the results with 29 completed full-history reference traces, comprising 25 target pairs. The eligible candidate hashes and line counts matched in every case. The graph boundary excludes ancestry with no eligible targets; it does not use an approximate timestamp cutoff. See [Git's documented revision-range behavior](https://git-scm.com/docs/git-blame#_specifying_ranges).

The pipeline excludes blank deleted lines but has no language-aware filter for comment-only changes. The human run does not use a checked-out blame-ignore file. None of the 1,998 entries in the reference file (blob `d20aaada25a8911b835a738dd508e3064acccb2f`) occurs in the active human history after the graph boundaries, so this omission does not affect eligible human attributions. The supplied database does not record the original AI run's blame-ignore settings.

## Features and experiments

We calculate the 14 Kamei metrics using the team's Python history-replay procedure. History metrics use earlier non-merge history, including backouts and automation, because these commits changed the files. LT uses the contents of nonbinary changed files in each commit's first parent. Missing Git objects are fetched before computing LT. New paths and binary files contribute zero, following the team's pipeline.

NUC (NPT in the replication package) counts distinct last changes across the modified files, matching the paper's worked example on printed page 761; it does not count all historical touches. FIX follows the team's Bugzilla-`defect` proxy instead of the paper's message-keyword rule: Firefox uses bug IDs for tasks and enhancements as well, so the keyword rule would mark nearly every linked commit. This differs from the paper's rule and may include changes that are not genuine fixes.

Following the replication package, we divide LA and LD by the original LT when LT >= 1. We also divide LT and NPT by NF, and entropy by log2(NF) when NF >= 2. We apply these normalizations once. Metric names follow the package (`nm` = ND, `pd` = AGE, `npt` = NUC).

For RQ1, we use logistic regression with the transformations, correlation and VIF filtering, and BIC variable selection implemented in the replication package. We apply majority-class undersampling to the training folds and evaluate prediction performance using ten-fold cross-validation. For RQ2, we evaluate the supplied LR and EALR models and report recall at 20% effort and Popt. For RQ3, we fit the supplied regression procedures on the full dataset. Since these models use all available changes for training, their training performance is not an estimate of performance on held-out data. We report coefficients and odds ratios for the logistic models and linear coefficients for the EALR models.

For variable selection, we follow the supplied code, which uses `stepAIC(..., k=log(nrow(fit)))` and therefore applies a BIC penalty. This differs from the paper's description of Mallows' Cp.

We set the random seed to 1 for each model and stage to make the folds and sampling reproducible. Helper functions and metric conventions follow the original package, apart from the F1 correction below. Selected coefficients describe conditional associations; their magnitudes are not a scale-independent ranking of feature importance.

For each new cohort, we build one general model and models for its five largest products. We additionally build AI models for Toolkit and DevTools to support the team's matched-product comparison. Sparse subsets are included with their sample counts and warnings. The guideline of approximately 140 bug-inducing changes is a reference point discussed by the team, not an assignment requirement.

## F1 calculation and model warnings

The original `evalPredict` computes F1 as `2 * precision * recall / (precision + recall)`. When a fold has zero true positives but contains positive predictions and actual defects, both precision and recall are zero, so the expression produces `NaN`. We modify the copied helper to return F1 = 0 when both precision and recall are zero. We check the modified helper on the zero-true-positive case and confirm that it gives the original results for three other cases. The four affected AI RQ1 models were rerun using the same data, folds and seed; their fitted models and predictions are unchanged.

Sparse product models produce separation and nonconvergence warnings, which are recorded with the results. Their parameter estimates may be unreliable even when the reported metrics are finite. The AI Toolkit and DevTools subsets contain only 16 and 18 bug-inducing changes, respectively. These analyses should be treated as exploratory.
